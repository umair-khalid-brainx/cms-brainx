## Summary

Saved headers and footers ("chrome presets"), per page or post. `api` gets a `ChromePreset` model plus a
`content.chrome` JSON column, a `/chrome-presets` CRUD module, menus scoped by `presetId`, a footer bottom
line site setting, and a public `/chrome?path=` endpoint that resolves which header and footer a page shows.
`web` moves header and footer into `@header`/`@footer` parallel-route slots that call that endpoint. `admin`
adds a preset picker and text card on the Menus screen, and a "Header and footer" section in Page settings.

Stack: one git repo holding three projects. `api/` was reviewed against the NestJS criteria, `admin/` against
React, and `web/` (Next.js) against React plus general criteria. Cross-project contract: admin's `ChromePreset`,
`PageChrome` and `SiteDetails.footerBottom`, and web's `PublicChrome`/`PreviewPage.chrome`, match the API shapes
in this diff. The limits `PRESET_NAME_MAX`/`BOTTOM_TEXT_MAX` are copied by hand into admin (noted in a comment)
and currently agree.

Tenant scoping holds. Every new repository method takes `siteId`. Preset ids from the URL, the query string or
a page body are all checked against the caller's site. The raw `usage` SQL uses bound parameters.
