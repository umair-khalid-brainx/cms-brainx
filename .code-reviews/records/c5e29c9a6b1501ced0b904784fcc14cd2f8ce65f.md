## Summary

GOV-01: page and entry revisions. `api` adds a `revisions` table (migration + `Revision` model; `site_id`, `content_id`
cascade, `author_id` SetNull, index `(content_id, created_at desc)`), `RevisionRepository` (every method `siteId`-scoped;
insert + prune beyond 50 in one `$transaction`; in-place `overwrite` via `updateMany`), pure rules in `revision-rules.ts`
(`reasonForSave`, `decideRecording` with a 10-minute same-author autosave window, key-order-insensitive `snapshotsEqual`,
`splitRestorableTerms`), and `RevisionsService` + `RevisionsController` (`GET /content/:slug/revisions`, `GET .../:id`,
`POST .../:id/restore`). `ContentService.update` records a revision of the page as it now is, after the write, inside
`afterWrite` so a failure never fails the save. Restore keeps status and address, records `before_restore` first, re-sanitises
blocks, normalises SEO via `readSeo`, drops terms deleted since (reported as `droppedTerms`), needs `content:publish` for a
live page and holds a live page to the publish checks (`ContentService.publishChecksFor`, passed in as a callback to avoid a
service cycle), then revalidates page, listing and (when terms changed) the site. `admin` adds a History panel (native modal
`<dialog>`, grouped by day, nested confirm dialog), `revisions.ts` helpers with tests, `revisionsApi.ts`, and editor wiring
that flushes pending edits before listing/restoring and remounts Puck from the re-read page after a restore. Docs (D-062),
tickets and the previous review file's deletion are staged.

Stacks: no root marker (three independent projects, D-012). Reviewed `api/` as NestJS (nestjs.md) and `admin/` as React
(react.md). One git repository, so one review.

`admin`'s `RevisionSummary`; restore's `{restored, from{id,createdAt}, droppedTerms[{name,kind}]}` matches `RestoreResult`.

### Medium (1)
- **admin/src/pages/EditorPage.tsx:190** — After a restore whose re-read fails, `staleAfterRestoreRef` only blocks `handleChange`; `publishNow` still sends `latestDataRef.current`, which holds the pre-restore content, through `saveDraft` and `publishPage`. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `publishNow` now returns early when `staleAfterRestoreRef.current` is true (EditorPage.tsx:179), which covers both the `.editor-publish` button and Puck's wired `onPublish`, and the button is `disabled` on the same flag (:294; the failure path's `setSaveError` re-renders so the disabled state shows). `flushPending` cannot write stale content either, because `handleRestored` clears `dirtyRef` and `handleChange` refuses to set it while stale. Previous note: `handleRestored` sets `staleAfterRestoreRef.current = true` and, when `getPage` fails or returns null, leaves it set and shows "Reload this page before editing". The Publish button stays enabled, and `publishNow` (and Puck's wired `onPublish`) never checks the flag. One click writes the old editor content over the restore and publishes it. The restore is lost from the page; it survives only as a revision. Fix: return early from `publishNow` (and disable the button) while `staleAfterRestoreRef.current` is true, or move the guard into a shared "can write" check that `publishNow` and `flushPending` both use.

### Low (3)
- **api/src/revisions/revisions.service.ts:143** — A restore whose term is deleted between `findByIds` and the write fails on the FK with Prisma `P2003` and surfaces as a 500. `ContentService.update` maps the same race to a 409 "A category or tag was just deleted". *(consistency)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `restore()` wraps `content.update` and, when `links` is set and the error is a `PrismaClientKnownRequestError` with code `P2003`, throws the same `ConflictException` ("A category or tag was just deleted…") as `ContentService.update` (revisions.service.ts:144-163). Other errors are rethrown unchanged. Previous note: `content.update(siteId, slug, …, links)` runs `contentTerm.createMany` inside its transaction. A term removed in that window violates the FK, the transaction rolls back (so no data corruption), but the error is uncaught and the admin shows the generic "Couldn't restore" after a 500. A `before_restore` row has already been written. Catch `P2003` when `links` is set and throw the same `ConflictException` as `update()`.
- **api/src/revisions/revisions.service.ts:108** — `checkLive` is optional, so `restore()` silently skips the live-page publish checks for any caller that doesn't pass it. *(maintainability)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `checkLive` is now a required parameter (revisions.service.ts:109, no `?`), and it is called unconditionally for a live page (:121-126), so a new caller that leaves it out fails to compile. Previous note: D-062 makes "a live page is held to the publish checks" a rule, but the service only enforces it when the controller remembers to supply the callback. Today the controller always does. A future caller (a bulk restore, a GOV-02 "restore from compare" route) could leave it out and nothing would fail. Make the parameter required, or inject the checks behind a small interface/token so the rule can't be skipped.
- **api/src/revisions/revision.repository.ts:67** — An autosave overwrite replaces the row's content but keeps its `createdAt`, so the History list labels a version with the time of the first save in its 10-minute window while it holds the state of the last one. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. A new migration (`20261012180000_add_revision_updated_at`) adds `updated_at` and backfills it from `created_at`. The model declares it `@updatedAt`, which Prisma also sets on `updateMany`, so `overwrite` bumps it. `createdAt` still anchors the window and the order. The API returns it as `savedAt` in list, get and restore's `from`, and the admin History panel, confirm dialog and restore notice show `savedAt`. Previous note: "Restore the version from 10:00" can restore content saved at 10:09. Keeping `createdAt` fixed is what anchors the window (bumping it would let continuous editing extend one row forever), so the fix is not to bump it. Instead, add an `updated_at` (`@updatedAt`) column and show that time in the list and confirm. Or document in the panel that an autosave row holds the latest state within its window. The order of the list is unaffected because only the latest row is ever overwritten.
